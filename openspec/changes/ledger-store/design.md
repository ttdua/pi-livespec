## Context

Every record a tool reads back is today an own marked comment (`src/forge/markers.ts`): `readChangeSnapshot` (`src/engine/snapshot.ts`) lists the issue's comments through `CommentsCache`, keeps those of the current login with `filterMarked`, and exposes them as `ChangeState.marked`, an array in forge order. That array index is the only time order: `deriveUnitEvidence` (`src/evidence/unit-state.ts`), `reviewRounds`/`liftIndex` (`src/review/status.ts`), `reviewerRuns` (`src/review/round.ts`), the build loop (`src/subagents/build-loop.ts`), `parkedRecord` (`src/engine/parked.ts`) and `deps/follow-up.ts` compare moved kinds (`receipt`, `unit-start`, `decision`, `finding-summary`, `dispatch`) with kinds that stay on the forge (`parked`, `rebuild`, `stuck`, `lane`, `review-run`, `answer`, `stale`, `amendment`). The comment id is also a public identity: `finding_rebut <commentId>`, the verifier target `finding: <commentId>:<index>` (`src/tools/subagent-target.ts`), finding keys `<commentId>:<index>`, packet sources `comment:<id>` versioned by `updatedAt` (`src/subagents/sources-records.ts`), and comment links in `unit_finish`.

Since #70–#73 (merged before this change): `dispatch` also carries `RETRY` records from the resume fallback (`src/subagents/resume.ts`, `dispatch.ts`) and the in-flight guard (`src/subagents/in-flight.ts`) reads pending `QUESTION` records; reviewer packets group decision records into one optional `records:decisions` source naming each record id (`src/subagents/sources-records.ts`); `finding-summary` keeps `notes`/`reason`/`evidence`; the spec-diff cascade (`src/interaction/spec-cascade*.ts`) keeps its baseline (`requirements`, `requirement_scope`) on the approved plan `gate` comment.

Writers: `decisionComment` (`src/decide/records.ts`) via `plan-units-steps.ts`, `review/stages.ts`, `interaction/complete-{decide,overrides,amend}.ts` and `unit-finish.ts`; `dispatch`/`finding-summary` builders in `src/subagents/records.ts` via `dispatch.ts`, `run-record.ts`, `lane-ops.ts`, `subagent-answer.ts`, `finding-rebut.ts`, `review/stages.ts`; `unit-start`/`receipt` in `src/evidence/records.ts` via `unit-start.ts`/`unit-finish.ts` (receipt before the body tick, reconciled on rerun); `setCounter` (`src/engine/counters.ts`, no production caller). Git runs through `GitExec` (`src/engine/git-exec.ts`); the only `git push` path is `src/guard/push.ts`.

## Goals / Non-Goals

**Goals:**
- One ledger module that appends, reads, syncs and deletes `refs/livespec/<issue>`, used by every writer of the six moved kinds.
- Readers keep one ordered record list; ordering between ledger entries and forge comments stays causal.
- No lost record under concurrent appends from two clones or two worktrees of one clone.

**Non-Goals:**
- Moving other kinds, rendering ledger data for humans, migrating old comments (#60–#62). This includes the plan gate's cascade baseline (`requirements`, `requirement_scope`, proposed on #59 after #63): it is temporary state on the `gate` comment, and #61 removes it when gates become prose and one `gates.jsonl` entry holds the result, `head_sha`, `locked` and the baseline. Moving only the baseline now would split one approval over two stores and be replaced again in #61. The cascade reads only `gate`, `stale` and `amendment`, all still forge comments, so its behaviour does not change in this change; `lock.baseline.commentId` stays the `gate` comment id after the `commentId` to `ref` rename.
- Tool-level offline mode: every writing tool keeps refusing in read-only mode (`prepareWrite` → `requireWritable`), including tools whose writes are now ledger-only; only the ledger layer itself is offline-capable (appends never fail for reachability, pending entries sync later). Letting ledger-only tools run offline is a later change.
- Authenticating entry authors.

## Decisions

**D1. Ref, files and entry shape.** One ref per change, `refs/livespec/<issue>`, an orphan history in the clone's common dir (shared by every worktree and lane). Its tree:
- `ledger.yaml`: `{ schema: 1, issue }`, written by the first commit;
- `decisions.jsonl` (`decision`), `dispatch.jsonl` (`dispatch`), `findings.jsonl` (`finding-summary`): one JSON entry per line;
- `units/<U>.yaml` (`unit-start` and `receipt` of unit `U`): a YAML sequence of entries;
- `change.yaml` (`counter`): a YAML sequence of entries.
`gates.jsonl` has no writer in this change and is not created. The other #59 contents of `change.yaml` (base, digests, scenarios, tags, difficulty) come with #62.
An entry is `{ ref, kind, id, seq, at, after?, from?, data }`; `from` is the forge comment id a migration (#62) copied the entry from, never written by this change, and reference matching accepts `ref` or `from`, so #62 needs no rewrite of `rebuts`/`verifies`/`start` fields or of `finding:<commentId>:<index>` text already on the forge. `ref` is the unique entry id `<id>~<8 hex random>`, `id` the record id writers use today (for example `progress.U1`), `seq` the position in the ledger (1-based), `at` the ISO write time, `after` the causal anchor (D3). Files are only appended to; an entry is never rewritten except for `seq` during a replay (D5). Reading skips invalid entries with a warning and treats a bad `ledger.yaml` as an empty ledger, because anyone who can push `refs/livespec/*` can write it (D10). Alternative: one file per entry. Rejected at the brainstorm gate (layout, readability).

**D2. Commits by plumbing.** `GitExec` has no stdin, so plumbing uses files, the pattern `src/content/mirror.ts` already uses: the changed file content is written to a temp file and stored with `hash-object -w <file>`; the tree is built in a temp index (`GIT_INDEX_FILE`): `read-tree <tip>` (or empty), `update-index --add --cacheinfo 100644,<blob>,<path>`, `write-tree` (nested `units/` comes for free); then `commit-tree -p <tip>` (no parent for the first) and `update-ref refs/livespec/<n> <new> <old>` (empty old value for creation). Reads use `ls-tree -r` and `cat-file blob <sha>` per file. The real index and working trees are never touched, so it is safe in any worktree state. One function `commitEntries(n, base, entries[])` serves append (one entry) and replay (many). Author and committer are always `livespec <livespec@localhost>` through `GIT_AUTHOR_*`/`GIT_COMMITTER_*` env (git may guess an identity instead of failing, so a fallback check is unreliable; ledger commits carry no human identity anyway), and the message is `livespec: <kind> <id>`. A lost compare-and-swap (another local session moved the ref) rereads and retries, at most 5 times, then throws. Read results are cached in memory by tip SHA.

**D3. One merged record list with causal anchors.** `ChangeState.marked` becomes the merge of own marked comments and ledger entries. Each entry stores `after`: the ref of the latest own marked comment in the writer's state when it appended (absent when there was none). Merge: forge comments keep forge order; each entry is placed right after its anchor comment, entries with the same anchor keep ledger file order (the order of the entries in their files, never `seq`: a gap, repeat or reversal of `seq` invalidates nothing); an entry whose anchor is no longer among own comments falls back to the last own comment with `createdAt <= at`, and before every comment when there is none. Every "latest"/"newer" comparison, also between two entries, uses positions in this merged list, never `seq` alone (a replay can renumber `seq`). This is clock-independent in the common case (a session writes after reading), and a concurrent comment the writer did not see is ordered after the entry, which matches what the writer knew. Alternative: merge by timestamps. Rejected: same-second ties and clock skew between machines break `receipt` vs `rebuild`/`parked` comparisons. Alternative: move every machine kind now. Rejected: out of #59's scope.

**D3b. One reader seam.** Besides the snapshot, five paths read own records straight from the forge and would miss ledger entries: `interaction/poll.ts` (`readFresh`), `tools/decide-ask.ts` (`reuseAnswer`), `interaction/forge.ts` (open-request check), `evidence/wip.ts` (started units for the agent-skills upgrade rule) and `ship/feedback-poll.ts` (review round number). They all switch to `readOwnRecords(forge, ledger, n, comments?)`, which returns the same merged list as the snapshot; the snapshot passes its cached comments so the comments cache and its offline fallback keep working. `WorkInProgressFn` gains the ledger (the CLI path `commands/deps.ts` builds one with `createLedger(defaultGitExec, cwd)`); `createForgeApprover` gets the ledger for its open-request check. Paths that read only forge kinds (`change-start` parked, `spec-cascade` gate/stale/amendment, `initiatives/sync`, `ship/close`) stay as they are.

**D4. Record identity.** `MarkedComment.commentId` is renamed `ref` and gains `source: "forge" | "ledger"`; for a ledger entry `ref` is the entry id. The rename is mechanical and compiler-checked, and stops a ledger id being called a comment id. Public forms (approved): packet source `ledger:<issue>/<ref>` versioned by the SHA-256 of the sorted-key, whitespace-free JSON of `ref`, `kind`, `id`, `at`, `after`, `from` and `data` (without `seq`, so a replay keeps the version); `finding_rebut <ref> <index> ...`; verifier `finding: <ref>:<index>`; finding keys `<ref>:<index>`; `unit_finish` names records as `ledger:<issue>/<ref>` instead of comment URLs. `rebuts`, `reviews` and `verifies` fields hold entry refs. Inside `records:decisions`, each decision is named `ledger:<issue>/<ref>`; `RETRY` records keep `agentId`/`newAgentId` as today.

**D5. Sync: fetch, fast-forward, replay, push.** Remote is always `origin`; the remote-tracking copy is `refs/livespec-origin/<n>` (outside `refs/livespec/` so the guard rule stays simple). `sync(n)`:
1. `git fetch origin +refs/livespec/<n>:refs/livespec-origin/<n>`; a missing remote ref clears the tracking ref (`update-ref -d`, done by the sync, not by `ledgerFetch`); a transport failure ends sync as `pending`.
2. Local absent or ancestor of remote → fast-forward local by CAS. Remote absent or ancestor of local → go to 4.
3. Diverged → replay: the entries of local whose `ref` is not in remote, in local file order, are appended to the remote tip in one commit with new `seq` values and unchanged `ref`, `at`, `after`, `data`; local moves to it by CAS (a lost CAS restarts sync).
4. Local ahead → `git push origin <local>:refs/livespec/<n>` (no force). A non-fast-forward rejection restarts from 1, at most 3 times; a transport failure is `pending`.
Append runs sync best-effort after the local commit and never fails because of it. Result: `synced`, `pending` (local entries not on origin; offline, no `origin`, or retries exhausted) or `error`. Because entries are only added and merged by `ref`, no record is lost; a counter set concurrently from a stale read can lose an increment, as with today's last-write-wins comment edit.

**D6. When sync runs.** Fetch before first use: `Session.refresh` fetches by default; only the context hook and session start pass `{ fetch: false }`, so every tool path (including tools that call `refresh()` directly, such as `subagent_packet`, `read_change`, `change_start`, `plan_units`) fetches first. `prepareWrite` refuses before any other work when `ensureFetched` returns `unknown-offline`. The first state refresh of a change in a session runs `ledgerFetch` and fast-forwards (or replays) the local ref, and remembers success per session; later refreshes do no network I/O. A missing remote ref and a clone with no `origin` remote count as success. The session-start phase card reads the local ref and does not wait. On failure with a known ledger (local or `refs/livespec-origin/<n>`), tools continue with a warning; with no known ledger, `Ledger.append` refuses (an empty read would otherwise look like "no records" and fork the state, for example a second `unit-start`). Sync also runs after every append (best-effort), at session start for the current change (best-effort, not awaited by `session_start`, to push pending entries), in `change_ship` before the branch push (required, D7), and in `change_close` before deletion. Snapshots read only the local ref, so state reads do no network I/O; a pending sync is shown as a warning when the local tip exists and is neither `refs/livespec-origin/<n>` nor its ancestor.

**D7. Ship requires a pushed ledger.** `change_ship` syncs first (`settleLedger`); when the tip moved, the state is rebuilt. Then the refusal checks and freshness re-run. A second sync right before `guardedPush` refuses, naming the cause, if the tip moved or the sync is not `synced`, and pushes nothing. Reviewers on another machine then see every receipt and finding of a shipped change. `change_push` does not require it (later pushes add review-fix records that sync best-effort).

**D8. Guarded git paths.** `src/guard/push.ts` gains `ledgerFetch`, `ledgerPush` and `ledgerDelete`, each building its refspec from an issue number (a positive integer) only, remote `origin`. The ledger module is their only caller; the existing scan test is extended. `ledgerDelete` runs `git push --force-with-lease=refs/livespec/<n>:<tip> -- origin :refs/livespec/<n>`. The bash guard gains a rule that blocks any git command whose arguments contain `refs/livespec` or `livespec-origin`, except the read subcommands `log`, `show`, `cat-file`, `rev-parse`, `rev-list`, `ls-tree`, `ls-remote`, `for-each-ref`, `diff`; it also blocks `update-ref --stdin` and wildcard destination refspecs outside `refs/remotes/` on `fetch`. Other plumbing (`pack-refs`, `replace`), refspecs from git config, ref names behind shell expansions, unmodelled git subcommands, and direct writes to `.git` files are accepted limits, as for other refs (ADR 0004).

**D9. Forge markers for moved kinds.** The six kinds leave `CORE_KINDS`; `writeMarked` refuses a ledger kind; `filterMarked` drops comments of a ledger kind and adds one warning per kind (`ignored N <kind> comments: <kind> records live in the ledger`). No dual read (brainstorm gate).

**D10. Trust.** Entries carry no author check: whoever can push `refs/livespec/*` to `origin` can write state, the same set of people who can push branches. Human authority stays on the forge (gates, answers). Recorded in ADR 0008.

**D11. Retention.** Project config `ledger: { retain: boolean }`, default `true` (project, not user: it governs a shared remote). With `false`, `change_close` adds a step after closing the change issue: sync, `ledgerDelete`, then delete the local and tracking refs. A failed remote delete does not fail the close; the tool result names it, the local refs are still deleted, and the step is skipped on a retry once the local ref is gone. Accepted limits: a remote ref left by a failed delete, a ledger another clone pushes again later, and `--abandon` closes keep their ledger.

**D12. Writer seam.** `Session` gains `ledger: Ledger` (built from the session's `GitExec` and cwd). `WriteContext` gains `ledger`. Each writer swaps `forge.createComment(n, writeMarked(...))` for `ledger.append(n, { kind, id, data, after })`, where `after` comes from the state it read; tools then refresh state as today (`afterLedgerWrite`, which skips the comments-cache invalidation). Completion: `CompletionCtx` gains `ledger`, filled by `sessionCompletionCtx` and the poll; `ApplyFn` returns `Promise<ResultRecord>` where `ResultRecord = { comment: string } | { entry: AppendInput }`, and the dispatcher posts or appends it last; `appendRecord(run, input)` appends and pushes the merged record into `run.marked`. A `decide:` request is completed when its `decision` entry is in the merged list (approver-adapters "Durable answers"). Module-load `registerKind` calls for `unit-start` and `dispatch` are removed when markers stop accepting ledger kinds; the ledger kind list lives in a neutral module `src/core/record-kinds.ts` that both `forge/markers.ts` and `src/ledger/` import. Builders keep returning data; marker formatting is removed for the moved kinds. Ordering with body writes is unchanged: the receipt append precedes the tick, decisions precede the `plan_units` body write.

## Risks / Trade-offs

- [In-flight changes lose state] → breaking note in CHANGELOG and ADR; finishing on the previous version or #62 migration.
- [A second machine reads an empty ledger before fetching] → fetch before first use (D6); appends refuse with no known ledger.
- [Entry written while the login is unknown has no `after`] → such an entry falls back to `createdAt <= at` placement like a lost anchor, instead of sorting before every comment.
- [Agent passes the ledger ref through a shell expansion (`git update-ref "$R" HEAD`) or an unknown git subcommand] → accepted limit of the guard, like other obscured forms (ADR 0004); the bash guard is a policy boundary.
- [Tests race the non-awaited session-start sync] → `Session` exposes the in-flight sync promise; the harness awaits it.
- [A stale `after` anchor places an entry too early] → writers pass the anchor from the state they just refreshed; tests cover entry vs later `rebuild`/`parked` ordering.
- [Two sessions on different machines append offline for a long time] → replay merges by `ref`; `seq` is renumbered, so nothing references `seq`.
- [Push fails silently while offline] → state warning while pending; `change_ship` refuses until synced.
- [Guard rule over-blocks a legitimate read] → read subcommands allowed explicitly; reported as `livespec guard:` with the reason.
- [Large rename `commentId` → `ref`] → done first as a pure refactor task with the suite green before behaviour changes.
- [git without new plumbing] → only `hash-object`, `read-tree`, `update-index`, `write-tree`, `commit-tree`, `update-ref`, `ls-tree`, `cat-file` are used; all are ancient.

## Migration Plan

1. Ship the ledger with the new version; ADR 0008 and CHANGELOG mark the change as breaking for in-flight changes.
2. Rollback: an older version ignores `refs/livespec/*`; records written meanwhile are invisible to it, so a rollback mid-change has the same effect as the upgrade (finish the change on one version).
3. No data migration in this change (#62).
