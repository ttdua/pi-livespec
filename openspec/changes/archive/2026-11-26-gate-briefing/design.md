## Context

Every human decision is an `ApprovalRequest` (`src/interaction/approver.ts`) built by one of five producers: `spec_gate` and the named-gate proposers (`gateRequest` in `src/tools/spec-gate.ts`), `unit_amend` (`src/tools/unit-amend.ts`), `spec_question` (`src/tools/spec-question.ts`), `spec_stuck` (`src/tools/spec-stuck.ts`, also called by `unit_finish` through `stuckFor` in `src/subagents/finish-freshness.ts`) and rule asks (`decisionRequest` in `src/tools/decide-ask.ts`). `prepareRequest` (`src/interaction/requests.ts`) turns it into the durable `RequestRecord`; the forge adapter stores that record as yaml under a marker and appends `plainText(r)`; the in-session adapter shows `r.summary` as a `select` title. Options are `{ id, label }` and only `spec_stuck` has a `recommended` id. `untrusted()` (`src/hooks/phase-card.ts`) already wraps foreign text for the agent, but nothing neutralises text that a human reads on the forge.

## Goals / Non-Goals

**Goals:**
- One `Briefing` shape carried by every request, stored in the record, rendered by both adapters.
- The recommendation is always one of the offered options, and nothing in the briefing can be read as an answer, a marker or a command.
- Forge request comments that a reviewer can act on from the comment alone.

**Non-Goals:**
- A `ctx.ui.custom` dialog (follow-up `rich-approver-dialog`).
- Changing the forge command grammar, answer validation, superseding or gate outcomes.
- Showing the recommendation on the phase card or in `/livespec next`.

## Decisions

**D1. One `Briefing` value on the request, stored in the record.** `RequestRecord` and `ApprovalRequest` gain an optional `briefing: { summary, watch?, recommended?, rationale?, author }`, where `author` is `agent` or `rule` and is set by the producer, never read from tool input; `RequestOption` gains an optional `description`. The briefing lives in the record (not only in the rendered text) so the `answer` comment, which copies the request, shows what the human saw, and a poll in a later session can re-render it. Alternative: put the briefing only in `summary` text. Rejected: it mixes trusted facts with agent text and cannot be validated or labelled.

**D2. Validation in one pure module, `src/interaction/briefing.ts`.** `validateBriefing(raw, choices, { author })` returns the normalised briefing or a refusal reason; callers check presence themselves (a required briefing that is `undefined` is refused by the caller, naming `briefing`), and an `author` key in the raw input is ignored. Rules: `summary` required, no blank line, at most 600 code points; `watch` 0-5 one-line items of at most 200; `rationale` at most 600, no blank line, required with `recommended` and refused without it; `recommended` must be an offered choice (built-in actions plus options for gates and amendments, options otherwise); option `description` one line of at most 200. Validation is shape-only and runs before any check or rule ask, so a bad briefing fails fast; the state-dependent rules (no `approve` recommendation while a waivable check fails, no `waive` recommendation when it is not offered) run after `planGate` in a separate pure `recommendationRefusal(briefing, plan)`; `planGate` itself does not change. `offeredChoiceIds({ kind, options, failingWaivable })` in `describe-actions.ts` is the single source of offered ids: before the checks `spec_gate` validates the shape against every id the target could offer (built-ins, `waive`, the registered options), after `planGate` against the real ones. Order in `runSpecGate`: require change → proposer refusal → resolve gate mode → briefing shape (human only) → behavior step / gate checks → refusals → `planGate` → `recommendationRefusal` → request. Every tool calls the same function, so the limits live in one place. Limits keep the forge comment and the dialog title readable; the numbers are this design's call.

**D3. Neutralise, do not escape.** Neutralisation covers all agent text in a request: the briefing, option labels and descriptions, question candidates, and the stuck report's where/tried/hypothesis. This text is shown to humans, not parsed. `neutraliseBriefing` replaces `<!--` with `<!-​-` (zero-width space) and prefixes any line that starts with `/livespec` with a zero-width space, so a forge reader sees the same text but neither `parseMarked` nor `forge-match` can read it as a marker or a command (both match at line start). Alternative: HTML-escape like `untrusted()`. Rejected: escaped markdown renders badly on the forge and in the TUI. The neutralised value is what is stored, so the record and every render agree.

**D4. The facts stay first and are never re-worded.** Renderers place livespec's payload (`summary` computed by `gatePayload`, failing checks, waivable checks) before the briefing, and the briefing heading names its author: "Agent recommendation (agent-authored, advisory)" for tool briefings, "Livespec rule recommendation" for rule asks. The request `summary` keeps livespec's payload, which already includes subject text the agent gave as data (question text, stuck report), and never the briefing. A failing waivable check is shown by livespec in the checks section whatever the briefing says.

**D5. Who writes the briefing.**
- `spec_gate`: new `briefing` parameter; required when the plan is `human`, ignored for `self`. `recommended` may name any choice the request offers (`approve`, `changes`, `dismiss`, `waive` when offered, or an option the request offers, which for a proposer may be a subset of the gate's options); `approve` is refused while a waivable check fails (the same rule that hides plain approve).
- Proposer tools (`initiative_propose`, `new_dependency`): optional `briefing` passed through `sendNamedGate`.
- `unit_amend`: new optional `briefing` parameter. Optional, not required, because amendments are often raised from next-step instructions in the build loop where a short reason already exists; without one the request has no briefing section, so livespec never writes text that looks agent-authored.
- `spec_stuck`: each option requires `description`; new required `rationale`; the existing `recommended` maps into the briefing; `summary` is the existing `hypothesis`, so the hypothesis follows the 600-code-point limit. `stuckFor` supplies descriptions and a rationale and caps its list of stale sources to stay within the limit. `storedReport` reads with a lenient parser that skips only the description, rationale and length rules (where, tried, hypothesis, 2-3 options and a valid recommended are still required, so stored data that is invalid today stays unusable), so a report stored before this change can still be re-sent; only the tool parameters are strict. `stuckFor` caps its hypothesis by code points, truncating and appending `and <k> more`, because a stale entry can be a long error message.
- `spec_question`: optional `candidates` (2-4 `{ label, description }`), optional `recommended` (one of `A`..`D`) and `rationale`. Candidates become the request's options with ids `A`..`D` in the order given. Labels must round-trip through the `answer` parser (`src/interaction/commands.ts` joins words with single spaces and reads `--changes`/`--class` as flags): one line, no leading/trailing/repeated whitespace, no word starting with `--`, unique. `choose` never answers a question; candidates are answered with `answer`. In session, after a candidate is picked the adapter still asks whether the answer changes a requirement.
- Rule asks: `RuleResult.ask` gains optional `options[].description`, `recommended` and `rationale`; `decisionRequest` builds a briefing (summary = the ask's summary) only when the rule recommends, since otherwise it would just repeat the facts. `behavior-change` gives descriptions for `unchanged` and `changed` and no recommendation (it cannot know), so its request has no briefing. A rule that recommends an option it does not offer, or gives an option text that breaks the shape rules, is a programming error: `decide` runs `validateOptionTexts` and throws, as it does for an answer without a choice. Rules never see agent text.
- Existing scenarios in other specs that call `spec_gate` on a human gate are read as passing a valid briefing (stated once in phase-gates "Gate tool"); their tests pass a fixture briefing.

**D6. Built-in gate actions get fixed descriptions.** `gateChoices(r)` lists approve (omitted while a waivable check fails, in both adapters), request changes, dismiss, then `waive` once (taken out of the options, answered with `/livespec choose waive`), then the other options. These built-ins carry livespec-written descriptions derived from the target (for example, approve at `plan` "locks the unit digests and moves to build"; at `ship` "allows change_ship"). These are facts about the workflow, not agent text, so they live in the renderer (`src/interaction/describe-actions.ts`).

**D7. Forge plain text is rebuilt by a pure renderer.** `plainText(r)` becomes `renderForgeRequest(r)` in `src/interaction/forge-text.ts` producing, in order: `## Decision needed: <what>` heading; the facts (`r.summary` inside a section titled by kind, files, links); a checks table when the snapshot lists failing waivable checks; the briefing section; a "How to answer" table with one row per likely answer (each built-in action, each option, and for questions one prefilled `/livespec answer Q<n> <candidate label>` per candidate); and the full command list in a `<details>` block. Table cells escape `|` so agent text cannot break the table; the briefing is rendered as a blockquote (`> ` on every line) and code fences, headings and `</details>` in agent text are escaped, so agent text cannot add a section or close the command list; a re-sent old stuck report has no briefing and keeps the `Recommended:` line in its summary. Everything below the yaml is ignored by the parser today and stays so; the yaml now also holds `briefing`.

**D8. In-session stays on `select`/`input`.** Menu building (`menuEntries(choices, recommended)`) and title composition (`titleWithBriefing(r)`) are pure helpers in `src/interaction/menu.ts`, so `in-session.ts` keeps only the dialog flows. A question without candidates keeps its current menu (`answer now`, `answer later (non-blocking)`); with candidates the menu is the candidates, `write my own answer`, `answer later (non-blocking)`. Before the action menu, the adapter shows the facts plus briefing as the `select` title (the API has no separate body); menu labels become `<label> — <description>` with ` (Recommended)` after the recommended label, and the recommended entry is listed first. The `[id]` suffix disappears; `displayTable` still dedupes by position, and identity still comes from the menu table, never from parsing a label. Picking a candidate sets `answer` to its label.

**D9. Stored requests without a briefing still work.** Reading tolerates a missing `briefing` and missing `description`; renderers skip the section. Only the producers enforce presence. A pending forge request created before this change completes unchanged.

## Risks / Trade-offs

- [The agent writes a persuasive but wrong recommendation] → facts first, advisory label, failing checks stated by livespec, `approve` cannot be recommended while a waivable check fails; the human still sees the full payload.
- [Briefing text tries to fake a marker or command] → neutralised on input (D3), and `forge-match` only reads comments from writers anyway; the agent's text lives inside the plugin's own comment, which is never parsed as a command.
- [Required briefing makes `spec_gate` refuse for agents with old habits] → the refusal names the missing `briefing` field and its shape, and the tool description documents it, so one retry fixes it.
- [`select` title becomes long] → length limits (D2); the rich dialog in the follow-up change removes this limit.
- [Breaking `spec_stuck` parameters for callers outside the repo] → the only in-repo caller (`stuckFor`) is updated; livespec is pre-1.0 and the CHANGELOG states the break.

## Migration Plan

No data migration: new fields are optional when read (D9). Release notes list the breaking tool parameters (`spec_gate` on human gates, `spec_stuck`). Rollback is a plain revert; requests written with a briefing remain readable by the older code, which ignores unknown yaml keys.
